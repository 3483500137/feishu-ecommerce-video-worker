# MultiPost 安全重试设计

## 目标

在飞书“平台发布”表的现有“确认发布”单选列中增加“重试发布”选项，并保证：

- “是”只触发没有历史任务的首次发布。
- “重试发布”只触发已经失败且存在历史任务的发布记录。
- 每次重试只消费一次，不会被 worker 循环重复执行。
- 旧任务不再参与成功结果匹配，新任务使用新的任务 ID 和幂等键。
- CT-00008 先恢复成可诊断的“发布失败”状态，不在修复过程中自动再次发布。

## 方案选择

采用“同列命令模式”：

- `确认发布 = 否`：不发布。
- `确认发布 = 是`：批准首次发布。
- `确认发布 = 重试发布`：人工确认平台端没有对应作品后，发起一次受控重试。

没有新增独立的“重试发布”列，避免日常操作分散到多个字段。

未采用的方案：

- 清空任务 ID 和幂等键后重新选择“是”：无法区分误删与人工重试，容易重复发布。
- 自动重试所有失败任务：平台可能已经发布但回调丢失，自动重试有重复作品风险。

## 状态与触发规则

首次发布必须同时满足：

- 文案生成状态为“已完成”。
- 发布标题、发布文案、标签均完整。
- 确认发布为“是”。
- 发布状态为“待确认”。
- MultiPost任务ID 和幂等键均为空。

重试发布必须同时满足：

- 文案生成状态为“已完成”。
- 发布标题、发布文案、标签均完整。
- 确认发布为“重试发布”。
- 发布状态为“发布失败”。
- 至少存在 MultiPost任务ID 或幂等键，用于证明这是一条历史发布任务。

不满足条件时不创建新任务。

## 重试数据流

1. worker 识别到合法的“重试发布”命令。
2. 将旧本地任务标记为失败，原因记录为“由飞书发起受控重试”，使旧任务不再参与平台结果匹配。
3. 将重试次数加一。
4. 使用记录 ID、账号记录 ID、视频 URL 和本次重试序号生成新的幂等键。
5. 创建新的 MultiPost 任务 ID 和任务文件。
6. 回填：
   - 确认发布：是
   - 发布状态：发布中
   - MultiPost任务ID：新任务 ID
   - 幂等键：新幂等键
   - 重试次数：新次数
   - 失败原因：清空
7. 打开本地发布桥接页，交给 MultiPost 扩展执行。
8. 扩展成功回调后回填“发布成功”；失败则回填“发布失败”，但不会自动再次重试。

## CT-00008 修复

目标记录恢复为：

- 发布状态：发布失败
- MultiPost任务ID：`mpx-example-task-id`
- 确认发布：是
- 失败原因：任务已下发，但 MultiPost 扩展未完成实际发布或结果回传；已确认快手端无该作品，可在扩展重新加载后选择“重试发布”
- 保留原幂等键，防止“是”再次触发旧任务。

修复记录本身不会触发发布。重新发布由用户在飞书把“确认发布”改为“重试发布”后触发。

## 扩展要求

Chrome 必须加载工作目录中的解压扩展：

`vendor/MultiPost-1.3.8`

代码更新后在 `chrome://extensions` 对该扩展执行一次“重新加载”，使快手发布结果回传脚本生效。

## 测试

单元测试至少覆盖：

- 待确认、确认发布为“是”、无历史任务时返回首次发布。
- 有历史任务时再次选择“是”不触发。
- 发布失败、确认发布为“重试发布”、有历史任务时返回重试。
- 非发布失败状态选择“重试发布”不触发。
- 重试生成不同于旧任务的新幂等键。
- 重试开始后确认发布被恢复为“是”，避免循环重试。
- 旧任务被标记失败，新任务可以正常进入 dispatched/succeeded 流程。

验证阶段运行完整 `npm test`，并重新读取飞书字段和 CT-00008 记录确认写入结果。
